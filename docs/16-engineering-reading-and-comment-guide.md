# 16 工程阅读与注释规范

## 1. 目的

本规范适用于 PotatoLink 前端、后端和后续新增模块。目标是让开发者能够快速回答三个问题：从哪里开始读、按什么顺序读、业务为什么这样流转。

## 2. 模块必须提供的阅读入口

每个业务模块必须有一个稳定入口：

- Java 后端使用包级 `package-info.java`；复杂模块可再增加模块 README。
- 前端页面模块使用同目录 README 或入口文件顶部模块说明，列出页面、状态、API 与权限关系。
- 中央业务规则以本仓库文档为准；代码注释引用文档章节，不复制大段易过期规则。

推荐阅读顺序固定为：

```text
模块说明
  → Controller / 页面路由
  → Request Contracts / 前端类型
  → Application Service / 页面状态编排
  → Repository / API Client
  → Domain Models
  → 数据库迁移 / 状态存储
  → 自动化测试
```

新增模块时，必须在模块入口写明：模块职责、明确不负责的内容、关键业务主线、权限边界、推荐阅读文件顺序。

## 3. 注释要求

必须注释的内容：

1. 事务边界以及失败时为什么必须整体回滚。
2. 库存、金额、状态机、权限与数据范围等关键业务约束。
3. 并发控制、锁顺序、幂等、重试和防重复处理原因。
4. 为兼容历史数据、外部系统或演示环境而存在的特殊处理。
5. 看似可以简化但不能简化的实现，以及对应风险。
6. 公共接口、复杂领域方法和不直观的数据结构。

不建议注释的内容：

- 对变量名和语句的逐字翻译。
- 已由类型、校验注解或清晰方法名表达的显然逻辑。
- 容易与实现脱节的长篇流程副本。
- 没有负责人和清理条件的模糊 `TODO`。

注释应解释“为什么”和业务后果，而不只是描述“做了什么”。修改业务逻辑时必须同步修改相关注释、模块入口、测试和中央业务文档。

## 4. 业务逻辑说明模板

复杂功能在模块入口至少包含以下内容：

```text
业务目标：解决什么实际经营问题
入口角色：谁触发，谁可查看，谁可审批
前置条件：状态、资料、库存或权限要求
主流程：按业务动作顺序列出
状态变化：原状态 → 新状态
数据副作用：库存、金额、文件、通知、审计如何变化
异常与补偿：失败、重复请求、超时、取消如何处理
验证入口：对应自动化测试或验收步骤
```

## 5. PotatoLink 当前模块阅读顺序

后端建议顺序：`identity → catalog → supply → file → inquiry → quotation → order`。其中 `common` 是横切基础能力，可在遇到认证、错误码、雪花 ID、分页等引用时按需阅读。

业务主线建议顺序：公开品种/批次 → 客户询价 → 内部分配与跟进 → 报价审批和发送 → 客户安全链接反馈 → 报价接受建单 → 批次临时锁定 → 合同或定金确认 → 履约节点和客户订单页。

## 6. 代码评审检查项

- 是否提供模块入口和推荐阅读顺序。
- 是否能从代码定位对应业务规则和状态机文档。
- 关键事务、并发、幂等和权限逻辑是否有原因注释。
- 接口、实现、迁移和测试是否保持一致。
- 是否保留历史审计，避免通过覆盖或删除伪造业务过程。
- 是否补充成功、越权、状态冲突、重复请求和库存不足测试。
